## Decisões de design (fixadas)

**D7.5.1 — Cancelamento de pendência exige motivo.** `alterarPendenciaSchema` ganha `superRefine`: `status === 'cancelada'` sem `detalhe.motivo` (string ≥ 5) → erro Zod 400. Não é breaking: o único chamador é a UI desta onda. Demais transições seguem com `detalhe` livre.

**D7.5.2 — "Marcar como resolvido" usa o endpoint existente** `PATCH /comercial/overbooking/:id/status` com `{ status: 'resolvida', detalhe: { origem: 'manual' } }`. `TRANSICOES_PENDENCIA` (dto/overbooking.dto.ts:60-79) hoje NÃO permite `aberta|em_analise → resolvida`; adicionar `'resolvida'` aos arrays de `aberta` e `em_analise` (o protótipo permite resolver manualmente a qualquer momento antes do encerramento). Histórico já é gravado pelo service.

**D7.5.3 — Postergação parcial é só UI.** `decidirPendenciaSchema` já aceita `quantidade` livre (regex decimal). O modal do protótipo entra com input controlado (`min=1`, `max=Number(quantidadeDeficit)`); envia a quantidade digitada em vez do déficit total.

**D7.5.4 — Timeline de Aprovações lê `historico` do detalhe.** `GET /operacao/ocorrencias-fornecedor/:id` já devolve `with: { historico: true }` (`ocorrencia-fornecedor.service.ts:49-52`). O client busca o detalhe ao selecionar a ocorrência e renderiza `historico[]` (`acao`, `situacao`, `createdAt`) como timeline + bloco de resultado quando `status === 'resolvida'` (`desfecho`, `dataHoraEncerramento`). Rota BFF `GET /api/operacao/ocorrencias-fornecedor/[id]` já existe (repasse).

**D7.5.5 — Simulador de Compras usa `POST /regras-desdobramento/simular`** (existente, `RequirePermissoes('REGRAS_DESDOBRAMENTO_LER')` — perfis `compras`/`gestor`/`administrador` já têm). O client soma as simulações de todas as linhas com `itemCompraId` e `quantidade > 0` (debounce 400ms) e renderiza no painel direito quando a compra ainda não está confirmada; depois de confirmada, mantém o comportamento atual (disponibilidade real). BFF `POST /api/cadastros/regras-desdobramento/simular` já existe.

**D7.5.6 — Colunas da tabela de itens de Compras.** "Regra de Desdobramento" = lista `descricao × fator` do retorno de `simular` para o item da linha (cache por `itemCompraId`); "Previsão (kg)" **não** existe no modelo real (peso médio é mock do protótipo) → coluna entra com valor `—` e `title="Previsão de peso depende de cadastro de peso médio por item — pendente"`; **proibido** inventar pesos.

**D7.5.7 — Teste de concorrência `registrarNf`.** Integration real: 2 × `POST /operacao/pedidos-fornecedor/:id/nf` em `Promise.all` com o MESMO `numero` sobre recebimento recém-iniciado (cabeçalho órfão criado via 1º registrarNf com `confirmarSubstituicaoCabecalho` — ver fixture na T4). Aceite: entre as duas respostas simultâneas com numeração divergente sobre o órfão, exatamente uma 2xx e uma 409 `CABECALHO_ORFAO_DIVERGENTE`, e ao final existe exatamente 1 NF ativa com itens para o recebimento.

**D7.5.8 — Badge Provisório condicional (AD-09) — redação da Emenda 1.** `{selecionada.localEstoquePrevisto?.provisorio && <Badge variant="outline">Provisório</Badge>}`. O contrato de tipo (`lib/operacao.ts:511`) é `{ valor: string | null; provisorio: true } | null` — os dois únicos estados válidos são objeto com `provisorio: true` ou `null`. Asserção no teste do componente: com `localEstoquePrevisto: { valor: null, provisorio: true }` badge presente; com `localEstoquePrevisto: null` badge AUSENTE (a seção Estoque renderiza sem o badge). Nenhuma mudança de tipo.
