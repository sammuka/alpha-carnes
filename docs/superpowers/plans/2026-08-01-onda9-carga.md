## Decisões de design (fixadas — só reabrir se houver quebra)

**D9.1 — Mapa de status caminhão → rótulos do protótipo (fonte única no frontend).**
`lib/expedicao-ui.ts` exporta:
```ts
export const ROTULO_STATUS_CARGA: Record<StatusCaminhao, string> = {
  planejado: 'Montando', aguardando_carga: 'Montando', em_carga: 'Montando',
  em_conferencia: 'Em Conferência', fechado: 'Conferida',
  liberado_faturamento: 'Enviada para Faturamento', faturado: 'Faturada',
  liberado_saida: 'Liberada para Saída', expedido: 'Expedida',

```
"Pronto para conferência" (planejamento) = `em_conferencia` (o botão "Enviar para conferência" chama `POST .../conferencia/iniciar`, que transiciona `em_carga → em_conferencia` — semântica real do F5; o rótulo do protótipo mapeia para esse estado). "Aguardando Conferência" (tela 24) = `em_carga` com carga aberta. Zero estado inventado.

**D9.2 — Nova permissão `EXPEDICAO_LER` (leitura das telas de carga) — redação da Emenda 1.**
Hoje `GET /caminhoes` exige `EXPEDICAO_GERENCIAR` — a matriz (linhas 23–25) dá consulta a `conferente` e `gestor` além de `expedicao`. Nova permissão `EXPEDICAO_LER: 'Consultar cargas, conferências e romaneios'`; GETs do controller passam a `@RequireQualquerPermissao('EXPEDICAO_LER', 'EXPEDICAO_GERENCIAR')`; mutações permanecem como estão. `pushPermissoes`: `conferente` ganha `EXPEDICAO_LER`, `EXPEDICAO_GERENCIAR` e `LEITURA_MANUAL` (é o papel operador da bipagem — doc 04 §6.2; escopo amplo aceito e registrado, espelhando o que o F5 já concede a `expedicao`); `logistica` e `faturamento` ganham `EXPEDICAO_LER` (consulta das telas 24/25 conforme matriz); `gestor`/`administrador`/`expedicao` ganham `EXPEDICAO_LER` (já têm GERENCIAR).

**D9.3 — Reconciliação frota (matriz linha 23 ↔ 33).**
Migration `0025`: `caminhoes.frota_caminhao_id uuid REFERENCES frota_caminhoes(id)` (nullable — caminhão do dia pode ser avulso) + índice parcial. `criarCaminhaoSchema` ganha `frotaCaminhaoId: z.string().uuid().optional()`; quando presente, o service copia `placa` e resolve `capacidadeKg` da frota (retorno de listar/detalhar ganha `capacidadeKg: number | null`); quando ausente, `capacidadeKg: null` e a barra de ocupação da UI mostra `—` (sem % — **proibido** capacidade inventada). O form "novo caminhão" do planejamento vira select da frota ativa (`GET /api/cadastros/caminhoes` — CRUD Onda 3) + fallback "avulso" com placa/motorista manuais (comportamento atual preservado).

**D9.4 — Divergência formal na conferência (`carga_itens`).**
Migration `0025`: `carga_itens.status_carga_item` CHECK vira `('em_carga','conferido','divergente','removido')`; colunas novas `divergencia_motivo text` CHECK `IN ('peca_ausente','peca_errada','peso_divergente','etiqueta_ilegivel','avaria','outro')` (nullable) e `divergencia_observacao text`. Novo `POST /caminhoes/:id/conferencia/divergencia` body `{ cargaItemId: uuid, motivo: enum, observacao?: string }`: transação → caminhão `em_conferencia` (senão 409), conferência aberta (senão 409), item da carga do caminhão com status `em_carga` (senão 409 `ITEM_NAO_PENDENTE`), UPDATE `status_carga_item='divergente'` + motivo/obs, auditoria, evento pós-commit `CARGA_ITEM_DIVERGENTE { caminhaoId, cargaItemId, motivo, dataOperacao }`. `concluir` da conferência: `pendencias.faltas` continua = itens `em_carga`; itens `divergente` entram em `pendencias.divergentes` (novo array no JSONB, mesmo shape de `faltas` + motivo). **Finalizar exige 0 pendentes** (`em_carga`); divergentes NÃO bloqueiam a conclusão (protótipo `:270`: `podeFinalizar = pendentes === 0`, divergente conta como tratado).

**D9.5 — `GET /operacao/expedicao/envio-faturamento?dataOperacao=`.**
Novo método em `liberacao.service.ts` (`listarParaEnvio`): caminhões da data com `statusCaminhao IN ('em_conferencia','fechado','liberado_faturamento','faturado')` + agregados por caminhão: `pedidos: Array<{ pedidoVendaId, clienteNome, pecas: Array<{ etiqueta, produtoNome, peso }> }>`, `totalClientes`, `totalPecas`, `pesoTotal` (SUM `pecas.peso_original`/`subitens.peso` dos `carga_itens` ativos — join respeitando XOR: peso da peça quando `tipo_origem='peca'`, do subitem quando `'subitem'`), `envio: { dataHora, responsavelNome } | null` — **Emenda 1:** `dataHora` = `caminhoes.hora_liberacao`, que passa a ser ESCRITA pelo `liberarFaturamento` (Task 4 Step 4a — hoje nenhum código escreve a coluna); `responsavelNome` buscado em `auditoria` (tabela `caminhoes`, registro id, justificativa `'Liberação para faturamento'` → join `usuarios.nome`; ausente → `null`, UI exibe `—`). "Histórico de Envios" da tela = cargas com `hora_liberacao IS NOT NULL` da data.

**D9.6 — Bipagem fiel (input + Enter; campo vazio = próxima pendente).**
O protótipo permite bipar com campo vazio → confere a próxima pendente (`:239-249`). Isso é açúcar de UI sobre o contrato ADR-009: com código, o client chama `registrar-item` com `modoCaptura: 'manual_assistido'` exige motivo — **incompatível com fluxo normal**. Fixado o mapeamento real:
- Campo COM código digitado/escaneado (leitor USB emula teclado + Enter): `POST .../conferencia/registrar-item` `{ tipoOrigem, modoCaptura: 'automatico' }` **não serve** (o fake lê do leitor, não do input)… O contrato real (`etiqueta.service.resolverQr`): `automatico` → lê do gateway leitor; `manual_assistido` → usa `dto.codigo` + exige `motivo` + permissão `LEITURA_MANUAL`.
- **Decisão:** a UI de bipagem usa `modoCaptura: 'automatico'` acionado pelo botão "Bipar" quando o campo está vazio (leitor físico/fake fornece o código — produção real com scanner serial); quando o operador DIGITA um código no campo, é conferência manual assistida: modal pede motivo (rótulo "Leitura manual — informe o motivo") e envia `manual_assistido` + codigo + motivo (exige `LEITURA_MANUAL` — `expedicao` já tem). O `tipoOrigem` é derivado no client pelo prefixo do código? **Não** — o client não decide: tenta `peca` e, se o backend responder 404, tenta `subitem` (dois requests no pior caso; erro final = mensagem do backend). Comportamento "campo vazio = próxima pendente" do protótipo é ficção de mock → o equivalente real é o modo automático (scanner decide o que foi lido); a UI mantém o placeholder do protótipo e a mensagem ok/erro fiel.
- Excedente (peça de outra carga): backend já responde 409 (`Item não está vinculado a esta carga (excedente)`) → exibir a mensagem no banner vermelho fiel.

**D9.7 — Peso e prioridade no planejamento — redação da Emenda 1.**
Peso do pedido = SUM real de `pecas.peso_original` + `subitens.peso` dos `carga_itens` ativos (carregado); "kg previsto" de pedido NÃO ALOCADO não existe no modelo (peso nasce na pesagem) → o card do pedido exibe `Σ peças previstas` (COUNT itens `quantidadePedida`) e para kg exibe `—` com `title` "Peso real apurado na pesagem" (**proibido** peso médio inventado — mesma regra da Onda 8).
Prioridade: `pedidos_venda.prioridade` (integer, real — `pedidos.schema.ts:22`, já tipada em `lib/comercial.ts:112`) → badge no card via `rotuloPrioridade` da Emenda 1 (`>=3` ALTA / `===2` MÉDIA / `<=1` BAIXA / null → sem badge), estilos dos rótulos do protótipo `PlanejamentoExpedicao.tsx:83-95` mapeados a tokens do DS.
Agrupamento por rota usa `pedidosVenda.rotaPrevista` (campo real usado pelo client atual `planejamento-client.tsx:76-83`).

**D9.8 — Eventos novos.**
`eventos.ts`: `CARGA_ITEM_DIVERGENTE: 'carga_item_divergente'` (payload `{ caminhaoId, cargaItemId, motivo, dataOperacao }`). Handlers no gateway (padrão F5). Clients das 3 telas: `conectarRealtime(['dashboard'])` com refetch em `CARGA_ITEM_ADICIONADO|TRANSFERIDO|REMOVIDO`, `CONFERENCIA_CONCLUIDA`, `EXPEDICAO_FECHADA|REABERTA|LIBERADA_FATURAMENTO`, `CARGA_ITEM_DIVERGENTE`.

**D9.9 — "Enviar para Faturamento" (tela 25) = `POST /caminhoes/:id/liberar-faturamento`.**
Permissão atual `FATURAMENTO_GERENCIAR` (controller `:134`) — matriz linha 25 dá a ação a `expedicao`/`gestor`/`administrador`. Alterar para `@RequireQualquerPermissao('FATURAMENTO_GERENCIAR', 'EXPEDICAO_GERENCIAR')` (o marco é da expedição; faturamento também pode puxar). Transição exige `fechado` (F5) — o botão da UI habilita só em rótulo "Conferida" (= `fechado`), como o protótipo `:272`.
